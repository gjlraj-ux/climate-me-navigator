# Navigator review — 29 September 2026

Reviewed the published GitHub Pages site and source at `91f50979352900e3b3d15a411de89c921a3c4abd`. Findings below distinguish observed behaviour, implemented changes and further design questions. This is not a full verification of all 44 catalogue sources.

## Conceptual assessment

The sequence of decision, scope, scales/resources and plan is coherent. Separating evidence-generation scale from decision scale, retaining local processes, and explaining exclusions are useful design choices. The main gap is between selecting methods and specifying how evidence will inform a decision. The original result page hides the actual decision inside an accordion while foregrounding the six suggested components.

This revision keeps that decision visible and adds optional notes for the learning question, review forum/timing, subsequent decision and feedback to contributors. These are editorial design choices, informed by the emphasis on purpose, operationalisation and use of results in Price-Kelly et al. (2015), rather than claims of validated usability improvement. The six components are described as functions; one existing process can fulfil several functions.

The first required question now asks for the main use of evidence. This separates the broad matching category (such as accountability or learning) from the user's concrete decision. Narrative notes remain unscored and do not imply the algorithm understands that decision.

## Bugs and fixes

| Finding | Evidence | Change |
|---|---|---|
| Local-process names lose text | On the live site, a 243-character name was accepted by a field with `maxlength=4000`, then cut to 200 characters after reload. | Normalize selected names and saved local drafts using the same 4,000-character bound as the input. Previously truncated text cannot be recovered. |
| Review link hides its destination | On the live site, “Review data, timing and resources” opened Step 3 with “Refine the plan” still collapsed. | Expand the relevant section, move focus and scroll to it. Optional answer edit links follow the same pattern. |
| Back from the first step opens an unexpected reference section | The first step's Back handler routed to the context checklist, despite entry through the welcome page. | Return to welcome and preserve answers, including after reload. The checklist remains available through navigation. |
| Supporting tools receive an overly strong label | `confidenceFor` returned “Potential fit” for high-scoring tools without a primary-use match, contrary to the documented label rule. | Prioritise the “Supporting option” label for those tools. |
| Partial thematic coverage is not explicit | A tool tagged for one of several selected themes earns the scope weight without identifying uncovered themes. | Name absent theme tags in a warning. Scores and eligibility are unchanged. |
| File picker cannot reliably retry the same selection | The import handler did not clear the input after reading or rejecting a file. | Clear it in `finally`; preserve existing error reporting and separate-project import behaviour. |
| Print context omits optional matching assumptions | The answers summary rendered only five required criteria. | Include answered optional criteria, alongside the new evidence-use notes. |

## Validation

- Existing catalogue validation and stakeholder scenarios, plus a mixed adaptation/mitigation scenario.
- Project regressions for supporting-only labels and partial thematic coverage.
- DOM integration journeys exercise Back/reload; targeted navigation and focus; local draft restoration; project duplication and switching; JSON import; evidence-use notes in text, CSV, JSON and offline HTML; print expansion/restoration; unique IDs and valid label/description targets.
- Export tests include multiline content, literal markup and spreadsheet-formula escaping. They inspect generated content rather than an operating-system download dialog.
- The production site remains a single HTML file. jsdom is used only for development tests.

The live site's desktop appearance and the two reported interaction failures were inspected in a real browser. Browser policy blocked local-file previews of the revision. Its rendered layout, native keyboard behaviour, mobile/zoom layout, actual print pagination and assistive-technology behaviour therefore still need browser review. DOM tests do not establish those properties.

## Next design questions

1. **Institutional access before apparent fit.** The tested community-monitoring journey included CBIT as supporting capacity provision. GEF describes CBIT as support for developing countries' institutional and technical capacity for Paris Agreement transparency requirements (GEF Secretariat, 2022). My assessment is that the interface should eventually distinguish “directly usable here” from “available through a national partner.” Generic adjacent-scale warnings are insufficient to establish access. This revision does not invent new eligibility rules without reviewing each source.
2. **Show what a usable completed plan looks like.** Expand a worked example through a review meeting and a decision, including unresolved disagreement and a feedback route. Keep it explicitly illustrative. Test whether users can explain what they will do next after reading it.
3. **Distinguish a selected role from a completed design.** Consider explicit “already covered by another process” and “defer for now” choices, with reasons, so users do not read six slots as six mandatory acquisitions. Validate this with practitioners before expanding the state model.
4. **Test interpretability rather than completion alone.** Ask a small, varied set of intended users to explain a suggested component, reject an unsuitable one, change a resource assumption and identify who will act on the resulting evidence. This is a proposed next evaluation, not a claim that the interface has already passed user testing.
